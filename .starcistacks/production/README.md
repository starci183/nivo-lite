# production

The production environment of NIVO: **Docker Swarm on one Ubuntu VPS** (a single-manager swarm: orchestration without manager failover; a lost manager needs recovery or a replacement), with the Supabase Cloud project as the external datastore. Components: `ingress` (Traefik), `landing` (`nivo.vn` / `www.nivo.vn`), `web` (console on `app.nivo.vn`), `api` (`api.nivo.vn`), `openclaw` and `n8n` (SQLite on the persisted volume `nivo-engine_n8n-data`; there is no self-hosted Postgres). Only `ingress` publishes ports (80 and 443, host mode). The zone `nivo.vn` is at Tino. The stack source is `infra/swarm/stack.yaml`; each release is rendered with `docker stack config` and deployed by the **Deploy stack** workflow (`.github/workflows/stack-deploy.yml`). There is no compose project and no host crontab on the VPS any more; the compose model of the cutover is described in `be/docs/runbooks/cutover.md`.

## The seven commands

All commands run on the VPS manager, or anywhere with `DOCKER_HOST=ssh://<user>@<vps>` and the pinned host key in `~/.ssh/known_hosts`. `deploy/swarm/vps.sh` holds the operator ones; the release itself is the workflow.

| Command | What it does |
| --- | --- |
| prepare | `deploy/swarm/vps.sh prepare`: read-only checks (Ubuntu/Docker versions, linux/amd64, disk, ports, Swarm state, the external volumes and networks), then creates the four external volumes a fresh host lacks (`nivo-engine_openclaw-data`, `nivo-engine_video-cache`, `nivo-engine_n8n-data`, `nivo-edge_acme`). `vps.sh prepare --init-swarm` runs `docker swarm init` ONLY with `NIVO_SWARM_INIT_APPROVED=1`, the owner's one-time approval; an active swarm is never re-initialized. One-time host setup: `sudo install -d -o <deploy user> -m 750 /srv/nivo /srv/nivo/releases`. |
| doctor | `deploy/swarm/vps.sh doctor`: the same checks plus services, replicas, images, the managed secret and config counts; changes nothing. Before a release the workflow also checks the swarm state, `/srv/nivo/releases` and the volumes, and refuses to initialize a swarm itself. |
| up | Actions > **Deploy stack** > Run workflow (environment `production`, reviewers approve). Build and push the api, web and landing images to GHCR, render with digests, create the versioned secrets and configs, pre-pull, `docker stack deploy --prune --with-registry-auth`, observe convergence, verify, then accept. Input `retire_compose` is for the cutover window only (see below). |
| status | `deploy/swarm/vps.sh status` (services, tasks with errors, update state); `deploy/swarm/release.sh list` shows the stored releases and the `current` / `previous` pointers. |
| logs | `deploy/swarm/vps.sh logs <api\|web\|landing\|ingress\|openclaw\|n8n> [--since 10m]`. Operator tools: `deploy/swarm/jobs.sh stats\|failed\|open\|retry\|retry-failed` (resolves the api task and runs the `jobs` CLI group in it); `vps.sh tunnel n8n\|openclaw` for the n8n editor and the OpenClaw Control UI over `ssh -L`. |
| down | `deploy/swarm/vps.sh down` (`docker stack rm nivo`): the services go; the volumes, secrets and configs stay. To go back to the previous accepted release use the **Roll back stack** workflow instead. |
| verification | `node deploy/swarm/converge.mjs --since <instant>` (desired versus running replicas, update state, no failed or rejected task) then `node deploy/swarm/verify.mjs`: `api.nivo.vn` `/healthz`, `/readyz` and a GraphQL `{__typename}`, `nivo.vn` and `www.nivo.vn` `/health/live` (landing), `app.nivo.vn/health/live` (console), the `nivo.vn/login?x=1` 308 redirect to `app.nivo.vn/login?x=1`, the legacy `nivo.vn/healthz` path, OpenClaw reached by service DNS from the api task, and `jobs watchdog` printing exactly two integers. The workflow runs both; the manual smoke list is `be/docs/runbooks/cutover.md`, "Verify the system". |

## Owner actions (the only ones)

1. **DNS at Tino**: A records `nivo.vn`, `www.nivo.vn`, `app.nivo.vn` and `api.nivo.vn` pointing at the VPS (`103.142.27.9`). Nothing scripts DNS; receipt: `nslookup api.nivo.vn 1.1.1.1`. The ingress cannot obtain a certificate before this.
2. **Approve `docker swarm init` on the VPS, once.** The cutover script runs `deploy/swarm/vps.sh prepare --init-swarm` with `NIVO_SWARM_INIT_APPROVED=1` only with `--execute` and after the owner says yes. Creating a swarm is an effect with its own recovery: afterwards back up `/var/lib/docker/swarm` (`vps.sh backup --swarm-state`) and decide on autolock before adding nodes.
3. **GitHub environment `production`**: secret `SOPS_AGE_KEY`, `VPS_SSH_KEY`, `VPS_KNOWN_HOSTS`; variables `VPS_HOST`, `VPS_USER`, optional `ACME_EMAIL`; required reviewers. The age identity stays backed up (`secret.env`).
4. **Packages**: the GHCR packages `nivo-lite-api`, `nivo-lite-web` and `nivo-lite-landing` are created private by the first run; keep them linked to the repository.

## Custody

Secrets are kept ONLY as sops-encrypted dotenv files in `.starcistacks/production/secrets/<slug>.enc`. The age recipient is in `.sops.yaml`; the age identity is `SOPS_AGE_KEY` in the canonical StarCi runtime `.claude/secret.env` (the owner backs it up: losing it loses every sealed secret) and the GitHub environment secret of the same name. No `.env*`, `secrets.env` or `.secrets/` exists, and none may be created.

- Read or change a value: `starci app secret list|show|set production <slug>` (values travel through stdin and memory only).
- A release decrypts the members **in memory on the runner** and pipes each key into `docker secret create nivo-<key>-v<keyed hash> -` on the manager over the pinned ssh session (`deploy/swarm/provision.mjs`). The version is the first 10 hex of an HMAC of the key name and value under the age identity: a changed value is a new name; an unchanged one keeps its name, so a deploy restarts only what changed. The rendered stack keeps `{external: true, name: <runtimeName>}` and no value. The logical-name to runtime-name map is the `secrets` list of each release's `release.json` (names only).
- Services read `/run/secrets/<KEY>` through `<KEY>_FILE`. OpenClaw has no `_FILE` support: its entrypoint wrapper (`infra/swarm/openclaw/entrypoint.sh`) exports the gateway token and the provider keys from `/run/secrets` into the gateway process only.
- Rotation: `starci app secret set production <slug> ...`, commit, run **Deploy stack**. The new name is created and granted, convergence is observed, and only then does `deploy/swarm/prune.mjs` remove names that neither the accepted nor the previous release uses. A name is never reused.
- Local development uses the local Supabase stack and exported shell values, not these files.

## Releases, health and rollback

- **Immutable release.** A release is the rendered stack bytes (its sha256 is the release digest), the source commit, the api, web and landing image digests (the other images are pinned by digest in `stack.yaml`), the non-secret configuration digest, the secret and config runtime names, the migration and backup plan and the previous accepted release: `release.json`. It lands in `/srv/nivo/releases/<digest16>/` (read-only) before the deploy, and the `current` pointer moves only after verification (`release.sh accept`); `previous` keeps the last accepted release for a bounded rollback.
- **Health signals.** The container healthcheck is liveness (`/healthz` of the api, `/health/live` of web and landing, process-local: a Supabase outage never restarts a task). Readiness (`/readyz`: the database answers within 2 seconds) gates traffic at the ingress (Traefik health check in `infra/swarm/edge/routes.yml`) and the deploy acceptance, never a restart. Startup is the healthcheck `start_period`. Functional verification is `verify.mjs`.
- **Updates.** `api`, `web` and `landing` update start-first (`order: start-first`, `failure_action: rollback`, `monitor`, `max_failure_ratio: 0`, with `rollback_config`); the stateful services (`openclaw`, `n8n`) and the host-port `ingress` update stop-first because only one task may own a volume or a host port. A failed update rolls itself back; the workflow then deploys the previous accepted release again.
- **Job alerts** are raised by the api itself (an in-process monitor reads `job_stats()` every `JOBS_ALERT_INTERVAL`; over the limits it logs a `job-ops.alert.*` error event and writes an `app_errors` row, at most once per kind per 30 minutes). Limits: `JOBS_ALERT_FAILED_MAX` (20) and `JOBS_ALERT_STALE_SECONDS` (300), taken from the `stack` member's `JOBS_FAILED_ALERT` / `JOBS_STALE_SECONDS` when sealed. There is no host cron and no watchdog script.
- **Backups.** `deploy/swarm/backup.sh` (n8n database dump, the n8n and OpenClaw volumes, optionally `--swarm-state`), run by the operator or an external scheduler; copy the result off the VPS encrypted and prove a restore on an isolated host before trusting it. The job queues are in Supabase (its PITR).
- **Rollback boundary.** Redeploying a stored release restores service specifications and images. It cannot revert a schema change (migrations are forward-only) or recreate a removed secret. A data restore is a separate action with an explicit loss window.

## OpenClaw and the loopback rule

The OpenClaw gateway honours the scopes a client declares only for a loopback peer using the shared secret. The api no longer shares the gateway's network namespace; it connects to `ws://openclaw:18790`, service DNS on the private `agents` overlay network. The entrypoint wrapper starts a byte-for-byte TCP relay (`openclaw-relay.mjs`) that forwards to `127.0.0.1:18789` inside the OpenClaw task, so the gateway sees a loopback peer. The gateway token is still required, and only the api (and an operator tunnel) is on that network. This is verified on cutover day by the chat-turn smoke check (the reply is not `direct_fallback`) and by `verify.mjs`.

## The cutover window (compose to Swarm)

The running compose model is `nivo-edge` (Traefik), `nivo-engine` (api, openclaw, n8n, n8n-db; n8n's Postgres is not carried to the stack: n8n moves to SQLite on `nivo-engine_n8n-data`) and `nivo-web`, plus the host crontab line of the old watchdog. The Swarm stack reuses the same named volumes, so the data and the certificates survive and the compose model can start again.

1. Before: owner actions 1 to 3; `vps.sh prepare --init-swarm` approved and run; `/srv/nivo/releases` exists.
2. The **Deploy stack** run with `retire_compose` builds, pushes, renders, creates the secrets and configs and **pre-pulls every image** while the compose model still serves.
3. `deploy/swarm/cutover/retire-compose.sh --execute` (approved with `NIVO_RETIRE_COMPOSE_APPROVED=1`) stops web, then engine, then edge with `docker compose down` (no `-v`), and removes the `nivo-engine-watchdog` crontab line. The public door is down from here.
4. `docker stack deploy` starts the stack. The ingress binds 80 and 443 and serves the certificates already in `nivo-edge_acme`; the window is the start time of the tasks (about one to two minutes with the images pulled).
5. Convergence and verification, then acceptance. If the first release fails, the workflow runs `restore-compose.sh --execute`: it removes the stack and starts edge, engine and web again from `~/nivo-edge`, `~/nivo-engine/deploy` and `~/nivo-web`, and re-adds the watchdog line (the old model only).
6. `namnivo-web` (the standalone container of `nguyentuannam.org`) must join the attachable overlay network `nivo-edge-swarm` with the alias `namnivo-web`: set `networks.edge: {external: true, name: nivo-edge-swarm, aliases: [namnivo-web]}` in its compose file, or once `docker network connect --alias namnivo-web nivo-edge-swarm <container>`. Until then that one host answers 502; the nivo.vn hosts are not affected.
7. After acceptance the folders `~/nivo-edge`, `~/nivo-engine`, `~/nivo-web` and the old images stay until the cutover is accepted by the owner; then they are deleted by hand.
